# デバイス認証を採用する

Status: accepted

人間の認証は管理画面に限定し、M5Stack CoreS3などのデバイスが `ai-edge-server` のデータAPIを呼び出すときは、デバイス単位で認証する。初回登録は一回限りのペアリングコードで行い、デバイスごとの秘密情報をTLS経由で短命トークンへ交換する。単一の共有トークンやデバイス上のAIサービスAPIキーは使用しない。

## 決定

- 管理者は組織のSSO/OIDCで管理画面へログインする。
- デバイスは初回起動時に一回限りのペアリングコードを表示する。管理者が管理画面で承認する。
- デバイスごとに秘密情報を発行し、デバイス側は通常フラッシュ/NVSへ保存する。サーバー側では平文保存を避ける。
- デバイスはTLSで接続し、秘密情報を使って短命の不透明アクセストークンを取得する。
- アクセストークンの有効期限は15分を初期値とする。
- API呼び出しでは、サーバーがトークン、有効期限、デバイスの有効/無効状態を検証する。
- 初期スコープはテレメトリ送信と状態取得に限定する。制御操作や管理操作は別スコープ・別経路とする。
- デバイスがオフラインの場合はAPI操作を停止する。
- 失効はデバイス単位で行い、再登録時は旧デバイスを無効化して新しいペアリングを行う。
- デバイス以外の呼び出し元を追加する場合は、デバイス資格情報を流用せず、別のサービス認証を設計する。

## 選択しなかった方式

- 全デバイス共通のAPIトークン：1台の漏洩で全デバイスを無効化する必要があるため採用しない。
- デバイス上のユーザーJWT：M5Stack上で人間のログインを直接扱う必要がなく、管理画面のSSOと責務が重複するため採用しない。
- mTLS：より強いデバイス認証が必要になるまで、証明書発行・更新・失効の運用を導入しない。
- リクエスト署名：初期版では実装と時刻同期の複雑さを増やさない。

## 実装時の必須条件

- 実運用ではTLSのサーバー証明書検証を有効にする。PoCの証明書検証省略を公開運用へ持ち込まない。
- 秘密情報、アクセストークン、ペアリングコードをログへ出力しない。
- デバイスごとにレート制限と失効操作を設ける。
- AIサービスAPIキー（現在はGemini APIキー）はサーバーだけに置き、デバイスへ配布しない。

## 状態

このADRは設計上の合意を記録したものであり、既存の共有トークン実装を置き換える実装は未着手である。
